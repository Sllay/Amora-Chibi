# V1.0 — Cognitive Integration / Soul

Status: **release candidate em `feat/v1.0-cognitive-integration`**.

A V1.0 integra os subsistemas locais já existentes numa única mente comportamental persistente. O provider generativo continua sendo computação substituível; **não é a identidade da Amora e não é autoridade sobre memória, crenças, emoção, autonomia ou ações**.

## Escopo congelado da V1.0

A V1.0 fecha quatro pilares definidos antes da implementação:

1. **Cognitive Integration** — Context Compiler + Privacy Gate + Model Router + providers substituíveis.
2. **Cognitive Journal + Conversation History persistente** — causalidade interna separada do que realmente foi dito.
3. **Streaming cognition → streaming speech** — frases estáveis podem começar a ser entregues antes do fim da geração.
4. **Amora Voice** — TTS expressivo quando permitido, fallback local, ACK de entrega e barge-in real.

Também fazem parte do fechamento de estabilidade da V1.0:

- fala autônoma passando pelo estado cognitivo canônico;
- reflexão estruturada com gates locais;
- quota ledger, backoff e failover de provider;
- Cognitive Replay para certificação A/B sem alterar a mente;
- consentimento explícito para cognição remota;
- backup/restore do estado cognitivo;
- observabilidade e testes de regressão.

### Fora da V1.0

**Imagem, foto, câmera, screenshot e percepção visual avançada ficam para V1.1.**

Nenhum desses recursos é requisito de conclusão da V1.0 e não deve ser reintroduzido nesta versão por leitura de roadmaps antigos.

## Invariantes

- `ENTITY_AMORA` continua sendo a identidade canônica independentemente do provider.
- providers propõem linguagem, memórias candidatas, hipóteses e ações candidatas; subsistemas locais decidem o que é aceito.
- `AUTH` e `SECRET` não são enviados para providers cognitivos remotos e seu conteúdo é redigido no histórico/journal.
- disclosure e autorização de processamento remoto são decisões separadas.
- speaker ID não é autenticação.
- ações sugeridas por modelo nunca são executadas diretamente.
- crenças sugeridas por modelo entram, no máximo, como `HYPOTHESIS` temporária; nunca como `BELIEF` canônico direto.
- toda lógica de cooldown/backoff usa o `Clock`/TimeService da Amora.
- falha de provider não derruba o Core.

## Conversation History x Cognitive Journal x Memory

São três estruturas diferentes:

- **Conversation History:** o que entrou e o que a Amora efetivamente tentou/falou, com status de entrega.
- **Cognitive Journal:** decisões e causalidade observável do pipeline, com reason codes; nunca chain-of-thought oculto.
- **Memory:** somente conteúdo consolidado que passou pelo Memory Write Gate.

Uma resposta gerada não é automaticamente considerada falada.

O fluxo de entrega distingue:

```text
provider output
→ response plan
→ speech segment queued
→ speaking
→ spoken | interrupted | failed
```

Para Android TTS local, `UtteranceProgressListener.onRangeStart` permite registrar o prefixo conhecido que saiu antes de um barge-in. Para PCM remoto, onde não há alinhamento confiável texto↔áudio, o Core registra explicitamente `SPOKEN_PREFIX_UNKNOWN` em vez de adivinhar.

## Barge-in causal

Barge-in não é apenas `AudioTrack.stop()`.

Quando uma voz humana sustentada toma o turno:

1. o Android detecta energia humana sobre o residual de playback após Acoustic Echo Cancellation;
2. mantém um pre-roll curto do áudio humano para não perder o começo da interrupção;
3. interrompe TTS imediatamente;
4. envia cancelamento por um executor de controle separado da requisição longa de STT/cognição;
5. o Core cancela o stream cognitivo em andamento;
6. segmentos ainda pendentes viram `INTERRUPTED`/`CANCELLED`;
7. novos segmentos do turno cancelado não podem nascer;
8. `TURN_FINISHED` só é registrado quando a entrega está terminal.

## Autonomia generativa

Ações semânticas verificadas continuam passando pelo Turn Manager. Quando a cognição remota autônoma está explicitamente permitida, uma intenção como `initiate_contact` passa pelo Context Compiler e o provider formula a fala usando estado real da Amora.

Sem autorização remota autônoma, o sistema mantém o compositor local seguro.

Variável de ambiente:

```bash
AMORA_REMOTE_COGNITION_ALLOWED=true
```

O default é **false**.

## Reflexão estruturada

Providers com `REASONING` + structured output podem devolver propostas limitadas:

```text
memory_candidates
belief_hypotheses
action_suggestions
tone
```

Aplicação local:

```text
memory candidate
→ Memory Write Gate
→ aceita / rebaixa / rejeita

belief hypothesis
→ World Model
→ HYPOTHESIS temporária, não canônica

action suggestion
→ allowlist + identity gate
→ evento cognition.action_suggested
→ deferred_to_bdi ou rejected_by_local_gate
```

A reflexão também possui failover de provider. A seleção pinada usa `ContextVar`, então uma tentativa de fallback não muda o router visto por conversas concorrentes.

## Providers, quota e failover

### Cognição

- Groq: primary quando configurado/elegível.
- Gemini: fallback cognitivo quando `GEMINI_API_KEY` existe.
- fallback local: último recurso e caminho obrigatório quando processamento remoto não é autorizado.

O router mantém seleção por capability, privacidade, janela de contexto, streaming/structured-output, custo/qualidade/latência e quota.

Falhas antes de qualquer fala permitem failover. Depois que um provider já emitiu fala, a V1.0 **não costura a continuação de outro provider no mesmo turno**.

Backoff:

- `429`: `Retry-After` quando presente; default 60 s e quota temporariamente zero;
- outros 4xx: cooldown conservador;
- 5xx/timeout: backoff exponencial limitado;
- cooldown é calculado pelo Clock canônico, sem `sleep()` bloqueante.

Modelo Gemini cognitivo pode ser alterado por:

```bash
AMORA_GEMINI_COGNITION_MODEL=<modelo>
```

## Consentimento Android

O app Android possui a opção:

> Permitir cognição remota para minhas falas

Ela é **desligada por padrão** e controla `remote_processing_allowed` enviado ao Core depois do STT.

Essa opção não deve ser confundida com autorização do provider de STT/áudio, que é uma decisão separada.

## Cognitive Replay

Cada turno não sensível pode guardar localmente um snapshot do `CognitiveContext` usado na geração. O replay usa esse snapshot para comparar providers sem recompilar o estado atual.

Endpoint:

```text
POST /v1/cognition/replay/{turn_id}
```

Propriedades:

- não escreve Conversation History;
- não escreve novo Cognitive Journal;
- não cria memória;
- não altera World Model;
- não altera emoção, drives ou intenção;
- não contabiliza replay no model-usage ledger;
- respeita a autorização remota original;
- `AUTH`/`SECRET` não recebem snapshot replayável.

O objetivo é certificar que trocar provider muda capacidade/estilo, **não identidade**.

## Persistência

Schema atual: **10**.

Persistem em SQLite:

- conversation messages;
- cognitive journal;
- speech segments;
- model usage/quota signals;
- todo o estado canônico anterior da Amora.

Backup/restore deve preservar histórico, journal, snapshots locais de replay e usage ledger.

CI não substitui o teste acústico no aparelho real. Antes de promover a versão para release estável, executar no A15:

```text
[ ] parear app e Core
[ ] habilitar/desabilitar cognição remota e confirmar comportamento
[ ] fala BK → STT → resposta cognitiva → TTS local
[ ] fala BK → resposta Groq → TTS expressivo quando permitido
[ ] forçar falha/quota do primary → confirmar fallback
[ ] interromper TTS local no meio da frase → confirmar prefixo falado persistido
[ ] interromper TTS remoto → confirmar prefixo marcado como desconhecido, sem falsa precisão
[ ] interromper falando "Mas Amora..." → confirmar que o pre-roll preserva o início no STT
[ ] restart Core → histórico/journal/identidade continuam
[ ] backup/restore → estado cognitivo continua íntegro
```

Falhas acústicas específicas do aparelho devem ser corrigidas antes de marcar `v1.0.0` estável.
