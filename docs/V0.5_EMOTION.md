# V0.5 — Emotion / Appraisal

A V0.5 adiciona estado afetivo persistente e causal ao Core da Amora. Ela não afirma consciência ou sentimento subjetivo; implementa mecanismos comportamentais para que acontecimentos tenham impacto coerente ao longo do tempo.

## Regras canônicas

A arquitetura do projeto exige separação entre:

- appraisal;
- emotion event;
- target;
- cause;
- blame;
- intentionality;
- spillover;
- entity affect;
- global mood;
- relationship state.

O roadmap da V0.5 inclui appraisal, mood, entity affect e social bids. Drives e decisão autônoma continuam reservados para a V0.6.

## Appraisal

Cada acontecimento é avaliado por oito dimensões canônicas:

- `goal_relevance`;
- `novelty`;
- `expectedness`;
- `agency`;
- `control`;
- `intentionality`;
- `norm_violation`;
- `relationship_relevance`.

A implementação também recebe `outcome_valence` (-1..1), que representa se o impacto percebido foi favorável ou desfavorável. Isso não substitui as dimensões; apenas fornece a direção do resultado para o cálculo determinístico.

O `AppraisalEngine` não usa LLM nem aleatoriedade para escolher emoção. O mesmo input produz o mesmo appraisal.

Emoções iniciais da V0.5:

- `joy`;
- `gratitude`;
- `relief`;
- `anger`;
- `irritation`;
- `fear`;
- `disappointment`.

Appraisals de sinal muito baixo podem não gerar Emotion Event.

## Emotion Event

Um Emotion Event persiste:

- emotion;
- intensity;
- cause event / description;
- target;
- perceived agent;
- blame;
- intentionality;
- spillover;
- appraisal completo;
- privacy scope;
- timestamp;
- dedupe key opcional.

Quando existe `cause_event_id`, ele também é propagado para a cadeia causal do Event Bus.

`AUTH` é recusado antes de persistência afetiva.

## Global Mood

Mood é contínuo em três eixos:

```text
valence   -1 .. 1
arousal    0 .. 1
dominance -1 .. 1
```

Emotion Events deslocam o mood conforme intensidade e spillover. O estado depois decai para o baseline usando `TimeService`, nunca `sleep()` ou relógio paralelo.

Half-lives iniciais de implementação:

| eixo | half-life |
|---|---:|
| valence | 60 min |
| arousal | 30 min |
| dominance | 90 min |

Esses valores são parâmetros iniciais e podem ser calibrados por testes de comportamento no futuro.

## Entity Affect

Cada entidade canônica pode ter estado afetivo independente:

```text
anger
affection
trust
irritation
fear
gratitude
```

Exemplo estrutural:

```text
BK irrita Amora
→ affect[PERSON_BK].anger sobe
→ global mood piora parcialmente por spillover
→ affect[ENTITY_CHATGPT].anger não sobe
```

Isso preserva a diferença entre:

- “estou irritada” (mood/global spillover);
- “estou irritada com BK” (entity affect/target causal).

Affect também decai pelo `TimeService`. Estados transitórios têm decay mais rápido; `affection` e `trust` usam decay muito mais lento.

A V0.5 não grava `anger/affinity` dentro do Relationship Graph da V0.4. Relationship identity/provenance e affect continuam domínios separados.

## Social Bids

A V0.5 pode produzir intenções sociais candidatas:

- `express_gratitude`;
- `seek_contact`;
- `seek_repair`;
- `set_boundary`;
- `withdraw`.

Um Social Bid possui target, strength, reason, source Emotion Event, TTL e status.

Social Bid **não é ação**. A metadata registra explicitamente:

```json
{
  "candidate_only": true,
  "requires_v0_6_decision": true
}
```

A V0.6 (Drives + Utility + BDI + hysteresis) decidirá se um bid merece ação, silêncio, adiamento ou descarte.

Bids expiram; emoção passada não se transforma automaticamente em desejo eterno.

## Idempotência

`dedupe_key` impede que o mesmo acontecimento real seja processado duas vezes e duplique:

- Emotion Event;
- mudança de mood;
- mudança de entity affect;
- Social Bid.

Idempotência sobrevive a restart porque a chave é persistida no SQLite.

## Persistência — schema 5

Novas tabelas:

```text
emotion_events
mood_state
entity_affect
social_bids
```

Todos os estados vivem no mesmo arquivo SQLite do Core e entram no backup/restore consistente.

## Interfaces

CLI local:

```bash
amora emotion appraise "BK ignorou Amora de propósito" \
  --valence -0.9 \
  --target PERSON_BK \
  --agent PERSON_BK \
  --goal-relevance 0.9 \
  --agency 0.95 \
  --control 0.6 \
  --intentionality 0.95 \
  --norm-violation 0.85 \
  --relationship-relevance 0.95

amora emotion state
amora emotion affect PERSON_BK
amora emotion events --target PERSON_BK
amora emotion bids
```

API localhost autenticada:

```text
POST /v1/emotion/appraise
GET  /v1/emotion/state
GET  /v1/emotion/affect/{entity_id}
GET  /v1/emotion/events
GET  /v1/emotion/bids
POST /v1/emotion/bids/{bid_id}/consume
```

## Definition of Done da V0.5

A etapa só pode ser considerada encerrada quando forem validados:

- appraisal determinístico;
- target/cause/blame preservados;
- spillover altera mood sem culpar terceiros;
- entity affect isolado por entidade;
- decay via TimeService;
- idempotência persistente;
- Social Bids com TTL e sem ação automática;
- recusa de AUTH;
- restart preservando estado;
- backup/restore preservando emotion events, mood, affect e bids;
- API autenticada;
- CI Python 3.11–3.14;
- teste físico no Galaxy A15 após merge.
