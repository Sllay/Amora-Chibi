# V0.7 — Actions / Planner / Skills

A V0.7 transforma uma `Intention` persistente da Autonomy em um plano executável, passa cada ToolCall por gates locais e só considera a intenção concluída depois de verificar o efeito esperado.

## Fronteira

```text
V0.6 Autonomy
  Intention
     ↓
V0.7 Planner
  Skill / Plan
     ↓
Action Bus
  permission + privacy + risk + cost + idempotency + timeout
     ↓
Plugin Tool
     ↓
Execution Monitor
  observe / verify
     ↓
continue | retry | replan | ask | abort
```

A V0.7 não implementa voz natural nem Turn Manager. Intenções sociais verificadas viram `action.semantic_request`; a V0.8 decide apresentação/turn-taking/voz.

## Planner hierarchy

A arquitetura mantém a hierarquia canônica:

- reflexos: regras/FSM;
- objetivos simples/repetíveis: skills locais em estilo HTN;
- objetivos semânticos complexos: contrato opcional `SemanticPlanner`/LLM;
- ausência de semantic planner não é mascarada: o Planner retorna sem plano em vez de inventar execução.

Skills locais atuais:

- `core.semantic_intention`: traduz intenções sociais/expressivas para uma ação semântica verificada;
- `core.rest`: resolve intenção de descanso localmente sem bloquear a event loop.

## Plugin contract

`PluginManifest` declara:

- id/nome/versão;
- permissions;
- events;
- tools e schemas;
- cost;
- risk;
- timeout;
- health;
- execution scope (`local` ou `remote`).

Plugins são registrados explicitamente. V0.7 não carrega código arbitrário do filesystem.

## Action Bus gates

Antes de chamar qualquer plugin:

1. plugin/tool precisa estar registrado;
2. `AUTH` é sempre negado;
3. plugin remoto exige `remote_processing_allowed=true`;
4. todas as permissions precisam estar concedidas;
5. tool não idempotente exige `allow_non_idempotent=true` explícito;
6. risk precisa estar dentro de `max_risk`;
7. cost precisa caber no budget do contexto;
8. `execute()` roda com timeout;
9. exceções de plugin são isoladas e o texto bruto da exceção não é exposto.

O contexto padrão do Core concede apenas `core:action:semantic`, execução local, baixo risco, baixo custo e não autoriza ações não idempotentes.

## Execution Monitor

Sucesso do `execute()` não basta. O monitor exige:

- output esperado;
- `plugin.verify(...)` verdadeiro;
- timeout também para a verificação.

Falha pode resultar em `retry`, `replan`, `ask` ou `abort` conforme `RetryPolicy`. ToolCall usa ID estável por `plan + step`, permitindo efeitos idempotentes sob retry/replay.

## Persistência

Schema 7 adiciona:

- `action_plans`;
- `action_runs`;
- `tool_executions`.

Plano, execução, verificação e dedupe sobrevivem a restart e entram no backup SQLite.

Social Bids só passam de `pending` para `consumed` depois de uma execução completamente verificada. Selecionar intenção ou apenas criar plano não consome o bid.

## Interfaces locais

API autenticada:

- `GET /v1/actions/state`
- `GET /v1/actions/plans`
- `GET /v1/actions/executions`
- `POST /v1/actions/plan`
- `POST /v1/actions/execute`

CLI:

```bash
python -m amora.actions state
python -m amora.actions plan --dedupe-key demo-plan
python -m amora.actions execute --dedupe-key demo-execute
python -m amora.actions plans
python -m amora.actions executions
```

`amora-actions` é instalado como entrypoint em instalações novas; `python -m amora.actions` funciona imediatamente após `termux-sync` em venvs existentes.

## Invariantes

- Model/provider não executa tool diretamente.
- Plugin não é autoridade de identidade/memória/world state.
- Plugin quebrado não derruba o Core.
- Replay com a mesma run dedupe key não reexecuta a tool.
- Tool não idempotente é deny-by-default.
- `AUTH` nunca entra em tool execution.
- Intenção só é `completed` depois do efeito verificado.
- V0.7 produz ação semântica; fala/voz natural continuam na V0.8.
